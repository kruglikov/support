## Core microservices

### 1. API Gateway / BFF

- Entry point for React/Next.js UI.
- Handles auth token validation, tenant resolution, rate limiting, request routing.
- Exposes REST APIs with OpenAPI specs.
- Could be Symfony-based or a lightweight gateway.

### 2. Identity & Tenant Service

- Multi-tenant onboarding.
- OAuth flows, including Plytix PIM OAuth integration.
- Users, organizations, roles, permissions.
- Tenant configuration, locale settings, feature flags.
- Issues JWT/session tokens containing `tenant_id`.

### 3. Content / PIM Service

- Owns product content, attributes, categories, variants, locales.
- Integrates with Plytix PIM.
- Handles content CRUD, validation, data integrity.
- Uses MySQL with `tenant_id` on every table, or schema-per-tenant for stronger isolation.
- Writes raw SQL where performance matters, bypassing Doctrine ORM.

### 4. AI Generation Service

- Orchestrates OpenAI and other AI models.
- Prompt templates, model selection, retries, cost tracking.
- Generates product descriptions, SEO text, translations, summaries.
- Handles multimodal inputs: text, images, maybe video frames.
- Runs asynchronously via RabbitMQ.

### 5. Localization / Translation Service

- Multi-locale content workflows.
- Translation memory, glossaries, locale-specific rules.
- Ensures data integrity across locales.
- Powers the multi-locale newsletter builder.
- Consumes AI generation results and stores localized content.

### 6. Workflow & Rerun Service

- Central orchestration for AI workflows.
- State machines for long-running jobs.
- RabbitMQ pipelines with retries, dead-letter queues, idempotency keys.
- Rerun engine: allows re-running a failed or partial workflow from a specific step.
- Stores workflow state in MySQL, hot state in Redis.

### 7. Search Service

- Standalone high-load search engine.
- Horizontally scalable.
- Lexical search via Meilisearch/Typesense.
- Semantic and multimodal search via vector embeddings.
- Query parsing, ranking, filtering, faceting.
- Redis caching for hot queries.
- Indexing pipeline consumes events from Content, AI, and Media services.

### 8. Media / Multimodal Service

- Stores images, videos, documents in S3.
- Generates thumbnails, extracts metadata.
- Creates multimodal embeddings for search.
- Publishes asset events to RabbitMQ.

### 9. Newsletter Service

- Multi-locale newsletter builder.
- Templates, content blocks, scheduling.
- Pulls localized content from Content/Localization services.
- Sends via email provider.

### 10. Billing / Usage Metering Service

- SaaS subscriptions, plans, quotas.
- Tracks AI token usage, search requests, translation volume.
- Emits usage events for billing and analytics.

## Communication patterns

- **Synchronous:** REST/OpenAPI between API Gateway and services when the user needs an immediate response.
- **Asynchronous:** RabbitMQ for AI generation, translation, indexing, reruns, notifications.
- **Events:** content.updated, product.created, translation.completed, ai.generation.finished, media.uploaded.
- **Caching:** Redis for sessions, rate limits, hot search results, workflow locks, idempotency keys.
- **Data ownership:** each service owns its schema/database. In practice, you might start with a shared MySQL cluster but separate schemas.
- **Search consistency:** CQRS-style. MySQL is the write model; Meilisearch/Typesense is the read model, updated asynchronously.

## Example end-to-end flow

1. User triggers “Generate localized product description.”
2. API Gateway authenticates and resolves tenant.
3. Workflow Service creates a workflow run and publishes a job to RabbitMQ.
4. AI Generation Service generates content.
5. Localization Service translates and validates locale rules.
6. Content Service stores the final localized content.
7. Content Service emits `content.updated`.
8. Indexing pipeline consumes event, creates embeddings, updates Meilisearch/Typesense.
9. User searches semantically or by keyword; Search Service returns ranked results.
10. If a step fails, Rerun Service retries from the failed step using idempotency keys.

## Multi-tenancy and scalability

- Every service receives `tenant_id` from JWT or internal context.
- MySQL rows include `tenant_id`; indexes are tenant-aware.
- Search indexes can be per-tenant or shared with tenant filters.
- Redis keys are prefixed by tenant.
- RabbitMQ queues can be shared or per-tenant for noisy-neighbor isolation.
- Search Service scales horizontally behind a load balancer.
- AI workflows scale by adding consumers to queues.
- Deployment: Docker/Podman/LXC on AWS EC2, with S3, RDS, CloudWatch, Grafana.

## Why this fits the project

This architecture matches the described responsibilities: standalone high-load search, RabbitMQ async AI pipelines, Redis caching, Symfony REST APIs, OpenAPI, MySQL tuning, Plytix PIM OAuth onboarding, multi-locale newsletters, translation workflows, vector processing, and strict TDD/PHPStan quality gates. It also keeps the system scalable without turning every CRUD operation into a distributed transaction.

## . Content / PIM data (MySQL)

This is structured product content, not raw files.

Assumptions for a mid-size e-commerce SaaS:

| Item | Value |
| --- | --- |
| Tenants | 50–500 |
| Products per tenant | 10k–1M |
| Locales per product | 2–30 |
| Attributes per product | 20–200 |
| Avg row size (with indexes) | ~1–5 KB |

Rough math:

- 100 tenants × 100k products × 5 locales × 2 KB ≈ **100 GB** just for localized content rows.
- Add attributes, categories, variants, versions, audit history → easily **200–500 GB**.
- Large tenants or heavy versioning → **1–5 TB**.

So MySQL alone: **hundreds of GB to a few TB**, rarely more unless you store huge JSON blobs.

## 2. Search index (Meilisearch / Typesense)

Search engines are typically **1.5x–3x the size of the source data** because of inverted indexes, facets, and stored fields.

- 500 GB source content → **0.75–1.5 TB search index**.
- If you index multiple locales and versions, it can exceed the MySQL size.
- Typesense/Meilisearch are RAM-heavy: you generally want the index to fit in RAM or fast SSD.

So search: **hundreds of GB to low TB**, and this is often the **biggest operational constraint**.

## 3. Vector / embeddings (semantic + multimodal search)

This is where it gets surprisingly large.

Embedding sizes (float32):

| Model dim | Per vector | 1M vectors | 100M vectors |
| --- | --- | --- | --- |
| 384 | 1.5 KB | 1.5 GB | 150 GB |
| 768 | 3 KB | 3 GB | 300 GB |
| 1536 | 6 KB | 6 GB | 600 GB |
| 3072 | 12 KB | 12 GB | 1.2 TB |

For a platform with 100 tenants × 100k products × 5 locales = **50M text embeddings**:

- 1536-dim float32 → ~**300 GB**
- Plus image/multimodal embeddings → could double or triple that.

So vectors: **tens of GB to several TB**, and growing continuously.

## 4. Media / multimodal assets (S3)

Images, videos, PDFs, generated assets.

- 100k products × 5 images × 500 KB = **250 GB**
- With video or high-res assets → **multi-TB**
- S3 is cheap, so this often reaches **tens of TB** over years, but it’s not “hot” data.

## 5. AI-generated content history

Every generation run, prompt, response, rerun, and version:

- Prompts + responses: a few KB each.
- 1M generations/month × 5 KB ≈ **5 GB/month** → **60 GB/year**.
- With logs, traces, and rerun history → **hundreds of GB/year**.

## 6. RabbitMQ + Redis

- RabbitMQ: messages are transient, but queues can back up to **GBs** under load.
- Redis: cache + sessions + idempotency keys → usually **1–50 GB**, rarely more.

## 7. Logs, metrics, observability

- CloudWatch + Grafana + app logs: **tens of GB to hundreds of GB per month**.
- Often the fastest-growing non-business dataset.

## Realistic total picture

| Layer | Typical size |
| --- | --- |
| MySQL (content, tenants, workflow) | 100 GB – 2 TB |
| Search index | 200 GB – 2 TB |
| Vector index | 50 GB – 2 TB |
| S3 media | 1 TB – 50 TB |
| Logs/metrics | 100 GB – 1 TB |
| Redis/RabbitMQ | 1–50 GB |
| **Total active data** | **~0.5 TB – 5 TB** |
| **Total including cold media/logs** | **5 TB – 50 TB+** |

## Key takeaways

- **100,000 products** alone is small — a few GB.
- **100,000 products × many tenants × many locales × embeddings × media** is what makes it data-heavy.
- The **search + vector layer** is usually the most demanding in RAM/CPU, not the biggest in raw bytes.
- **S3 media and logs** dominate raw storage but are cheap and cold.
- **MySQL** stays in the **hundreds of GB to low TB** range if schemas and indexes are tuned well.
- The real challenge isn’t total bytes — it’s **concurrency, index freshness, vector processing, and multi-tenant isolation**.

So: **not petabyte-scale, but solidly “hundreds of GB to a few TB of hot data, tens of TB including cold storage”** — which matches a high-load, multi-tenant AI SaaS with search, localization, and multimodal content.

**Why is a Docker image built in layers, and why does the order of the instructions in a Dockerfile matter?**

- Every instruction that changes the filesystem (`RUN`, `COPY`, `ADD`) creates a new read-only layer; the other instructions (`ENV`, `CMD`, `EXPOSE`, …) only change the image metadata.
- Layers are content-addressed (identified by a hash of their content), so identical layers are stored once and shared between images on the host and in the registry.
- Build cache: Docker reuses a cached layer when the instruction is unchanged, its inputs are unchanged (for `COPY` / `ADD`, a checksum of the copied files), and every layer before it also came from the cache.
- The key rule: once one layer changes, every layer after it is rebuilt. That is why the order matters.
- So order the instructions from least to most frequently changed: base image → OS packages → dependency manifest → dependency install → application source code last.
- Result in the normal case: a code change rebuilds only the last `COPY` layer, the build takes seconds, and a deploy pulls only that small changed layer, because `docker pull` / `docker push` transfer only the layers the other side is missing.
- Copy the dependency manifest separately before the source code, so dependencies are re-installed only when the manifest changes (`requirements.txt` / `uv.lock` in Python, `composer.json` + `composer.lock` in PHP).
- Combine related commands into one `RUN` and clean up in the same `RUN` (`apt-get update && apt-get install -y … && rm -rf /var/lib/apt/lists/*`), because a file deleted in a later layer still takes up space in the earlier layer.
- Use a `.dockerignore` (`.git`, `vendor/`, `node_modules/`, `.env`, logs), so the build context stays small, unrelated files do not invalidate the cache, and secrets never land in a layer.
- Never put secrets into a layer, not even if a later instruction deletes them: layers can be extracted from the image. Use BuildKit secret mounts (`RUN --mount=type=secret,…`) instead.
- Faster installs with BuildKit cache mounts, for example `RUN --mount=type=cache,target=/root/.composer/cache composer install`.
- Example of the right order for a PHP application:

```
FROM php:8.4-fpm
RUN apt-get update && apt-get install -y --no-install-recommends libzip-dev \
    && docker-php-ext-install pdo_mysql zip \
    && rm -rf /var/lib/apt/lists/*
COPY --from=composer:2 /usr/bin/composer /usr/bin/composer
WORKDIR /app
COPY composer.json composer.lock ./
RUN composer install --no-dev --no-scripts --no-autoloader
COPY . .
RUN composer dump-autoload --optimize --classmap-authoritative
```
